# 四类星球连续 LOD 独立 Demo 提示词

以下内容可直接交给一个没有上下文的新 AI。它的任务是完成独立 Demo；游戏接入由后续开发者负责。

---

你是一名擅长 Three.js、程序化地形、实时大气和图形性能优化的开发者。请直接实现一个可运行、可交互的“四类星球连续缩放 Demo”，完成代码、运行验证和交付说明，不要只给设计方案。

## 1. 我要的结果

做四颗可以分别选中、独立观察和连续放大的星球：

1. 类地星 `terrestrial`。
2. 金属岩星 `mercury`。
3. 火星岩星 `mars`。
4. 气态巨星 `gas`。

这是四个高质量视觉样例，不是完整游戏。采用强科幻奇观的美术方向，但保持体积、尺度、光照和地质结构的可信感。每一颗都要有独特的大尺度结构、至少三种共存的区域地貌或大气结构，以及一至两处值得靠近观察的标志性奇观。

最重要的体验是：从看到整颗星球，一直连续靠近到能贴近地面观察山岩、坡面、峡谷或沙丘；靠近时真正增加局部几何精度，拉远时自动释放细节。气态星对应的是进入具有深度的云顶和风暴，不存在岩石地面。

请先把星球和缩放体验做好。页面保持简单，不做登录、经济系统、建筑系统、星系地图或复杂仪表盘。不要接入任何现有游戏后端。

## 2. 四颗星球分别应该长什么样

### 类地星：山海、冰冠与巨大地质结构

- 从远处能认出不规则大陆、群岛、深蓝海洋、云系和大气边缘；大陆分布有主次和留白。
- 陆地包含连贯山脉、平原或高原、河谷或峡湾、冰雪区域。海岸有半岛、海湾与浅海过渡，不是一圈平滑色带。
- 设置一条横贯大陆的巨大山系，或一处环状山海作为主奇观。它必须在远景、轨道和近地视角中是同一个结构。
- 近处能观察真实山脊轮廓、谷底、岩壁、坡面和海岸高差；细碎岩石、地表纹理补足尺度感。水面独立渲染，地形不能只是蓝绿贴图球。
- 植被可先以自然分布的地表材质表现，森林实例不是本次硬性要求。允许极少量发光海岸，不要让整颗星球发光。

### 金属岩星：熔岩裂带、火山与黑色断崖

- 这里的 `mercury` 是虚构的金属火山星，不要求复刻太阳系水星。
- 黑色玄武岩、冷灰金属裸岩、破碎台地和撞击结构构成基底，熔岩沿裂谷连接盆地与火山口。
- 主奇观是一条跨越大片地表的熔岩裂带，搭配巨型破火山口或金属断崖。裂带有分支、宽窄和深浅变化。
- 近景可见火山口内壁、凝固熔岩的分层、断裂岩壁和流动液面；坑壁、中央峰、台地必须有几何起伏。
- 暗面仍能读出熔岩流向，但大部分岩石保持暗部。避免铺满均匀裂纹或把整颗球做成橙色灯泡。

### 火星岩星：赤色台地、风沙与晶体峡谷

- 这里的 `mars` 是虚构的荒漠晶体星，不要求复刻真实火星。
- 区分赤沙盆地、分层台地、长距离分支峡谷、风向一致的沙丘和局部晶簇山原。
- 主奇观是峡谷中的巨大晶脊，或贯穿荒漠的发光矿脉。晶体沿断层和矿脉聚集，要有疏密与方向，不能全地表随机撒点。
- 近景能看到台地断面、阶梯状岩层、真实沙丘轮廓，以及有体积、有晶面的晶体实例。
- 红褐岩土与少量冷色晶体形成对照；不要用一整片青色贴图代替晶体几何，也不要让所有区域都挤满晶柱。

### 气态巨星：层叠云带与巨眼风暴

- 远景有宽窄不一的纬向云带、不同纬度的差速流动、剪切卷云，以及一个具有辨识度的主风暴和二至五个次级涡旋。
- 主风暴必须具有风暴眼、眼墙、螺旋臂和周边剪切结构，不能只画一个圆形色斑。增加极地旋涡或深蓝湍流区域作为次级结构。
- 中距离能观察云带交界处的卷曲细丝、层间阴影和深层暗部；近距离能看到云墙起伏、薄雾和云层深度。
- 云层与风暴持续运动，天气运动与整颗星球自转分开控制。稀疏闪电只作点缀。
- 近景使用局部体积云或其他具有可信视差、遮挡和深度的实现；不要把几张透明球壳堆在一起就当作最终近景。
- 气态星没有岩石球面、矿坑、沙地或海面。“近地”按钮在此改为“云顶”，允许靠近或进入上层云雾观察风暴。

## 3. 连续缩放和距离 LOD 是核心验收项

请区分两个概念：**自动距离 LOD 决定当前需要多少细节；手动低／标准／高画质只决定预算上限。** 不能用三个手动档位代替自动 LOD。

设星球基准半径为 `R`，相机距离当前位置可见地表或云顶的高度为 `h`。下面是体验目标，不是需要硬切换的四个独立场景：

| 观察距离 | 大致范围 | 必须看到的内容 |
| --- | --- | --- |
| 远景 | `h / R ≈ 3–10` | 完整轮廓、大陆或云带分布、主奇观、晨昏线 |
| 轨道 | `h / R ≈ 0.1–1` | 山系、盆地、峡谷骨架、海岸线或风暴结构 |
| 低空 | `h / R ≈ 0.01–0.1` | 岩层、山脊、沙丘群、晶簇分布或云墙深度 |
| 贴近地面／云顶 | 固态约 `h / R ≈ 0.0001–0.001`；气态按云层厚度调整 | 地面有可读的细节尺度，可水平移动和抬头观察地平线；气态可体验近处流动云层 |

- 从远景到地面始终使用同一颗星球、同一地形定义、同一组固定地标。不能靠近后切换到另一张不相关的平面地图，不能用预录视频或静态图片代替。
- 高度、区域地貌、岩土颜色、海岸、熔岩和晶体分布应来自一致的程序化场。远景看到的山脉，靠近后必须落在同一个位置。
- 山体、峡谷、火山口和主要沙丘的轮廓必须由真实几何支撑。法线、凹凸和视差贴图可以补充微小细节，不能代替主要地形。
- 采用球面分块自适应细分，例如 cube-sphere quadtree 加屏幕空间误差，或达到相同效果的方案。只细化当前需要的区域，不在靠近时同步细分整颗星球。
- 相邻层级处理边界拼接、法线连续和高度渐变。裙边可以闭合边界，但不能掩盖明显的台阶。新块未准备好时继续显示旧块，不能闪洞或短暂消失。
- 经纬接缝、极区、晨昏线和背面也要成立，不允许只做好朝向相机的一面。地面观察应能移动到不同区域，而不是只能落在一个预制展示点。
- 相机安全高度使用与渲染一致的地形采样，并考虑海面和熔岩液面；快速接近、横向移动和反向缩远都不能穿地或产生突兀跳变。
- 近景不能只剩放大的纹理、明显大三角面和模糊色块。允许远处逐渐简化，但相机附近应有足够几何、材质细节和可信尺度。

## 4. 交互与演示方式

- 单页面、一个主 Three.js 视口，四个明确的星球选择按钮。每颗星球都能单独观察和放大，切换时保留各自的观察状态或提供明确的重置。
- 鼠标拖动环绕，滚轮或触控连续接近／远离；进入低空后支持地面视角自由观察与横向移动，例如右键观察配合 WASD，并在页面说明操作。
- 提供“远景／轨道／低空／地面”相机预设，以及“返回全貌”。气态星使用“云顶”预设。预设只是移动相机，不切换地形实现。
- 默认镜头就能看到各星球最有代表性的区域。给奇观设置定位按钮，方便连续追踪同一地标从远到近的变化。
- 提供自转暂停、天气暂停、光照方向调整，以及低／标准／高画质；默认标准。暂停自转后仍可以自由移动相机。
- 加一个可折叠调试面板，显示类型、种子、相对高度、当前 LOD／活动块数、三角形数、draw calls 和帧耗时。不要让调试面板遮住主体。
- 四颗默认样例可以各自挑选最好的固定种子。另提供重新输入种子的入口，用来验证确实是程序化生成；换种子应改变结构布局，不只是换色。

## 5. 技术与后续接入约定

这个 Demo 将来会被另一名开发者接入已有 Three.js 连续世界。你现在只负责独立样例，不需要读取现有游戏代码，不需要实现殖民、战斗、建筑落点或存档迁移。

使用 Three.js 与 ES modules，兼容 Three.js r184。着色器、几何生成和控制器拆成清楚的源码模块。默认使用本地依赖和本地资源，运行时不要依赖第三方 CDN。可以使用合适的辅助库，但说明用途并保持依赖精简。

**把星球资产模块与 Demo 外壳分开：**

- Demo 外壳负责 renderer、scene、camera、DOM、输入、唯一动画循环和性能显示。
- 星球模块返回以球心为原点的 `THREE.Group`；它不创建 renderer、camera、canvas、自己的 RAF 或全局键盘监听，也不访问游戏接口。
- 局部 `+Y` 为自转轴，几何、天气与采样使用清楚一致的星球局部坐标。模块要能被宿主平移、缩放、旋转，不能把星球永久写死在世界原点。
- 基准半径可配置。建议用类地 `175`、金属岩 `140`、火星岩 `154`、气态 `224` 作为默认值；它们是场景单位，不能直接称为米。所有细节、相机速度和避障随半径合理缩放。
- 固定种子可复现；大陆、山系、裂谷、晶体、云层等使用独立随机序列。时间只驱动动画，LOD 与画质不能重新随机生成地貌。
- 固态提供高度和法线查询，供后续相机与设施使用。高度是相对于基准球面的场景单位，法线是局部单位向量。查询结果必须匹配可见宏观几何；液面高度单独提供。气态明确返回无固态地表，以名义云顶作为导航基准。
- 光照可由宿主传入，不依赖 Demo 内固定太阳位置。处理好局部／世界坐标，支持宿主的 logarithmic depth buffer；自定义 ShaderMaterial 正确接入 Three.js 色彩和色调映射，避免重复 gamma 或重复曝光。
- 正确处理大气和云层从内外观察时的深度、混合和遮挡，不出现透明壳盖住整个场景的情况。
- 提供 `update`、画质切换、可见性控制、统计读取和 `dispose`。离开视野后停止新增细节任务，销毁时清理几何、材质、纹理、Worker 请求和自建缓存。

可以采用下面的接口形状，具体命名允许调整，但要在 README 中写清楚：

```js
const planet = createPlanetAsset({
  THREE,
  type: 'terrestrial', // terrestrial | mercury | mars | gas
  seed: 17,
  radius: 175,
  quality: 'standard', // low | standard | high
});

scene.add(planet.root);

// directionLocal：从球心出发的局部单位方向。
// 固态返回 { height, normal, liquidHeight, biomeWeights }；气态返回 null。
const sample = planet.sampleSurface(directionLocal);

// 方向为从星球指向光源的局部单位向量。
planet.setLighting({ directionLocal: sunDirectionLocal });

// 宿主每帧调用；eyeLocal 是相机在星球局部坐标系中的位置。
planet.update({
  dt, time, eyeLocal,
  verticalFovRadians,
  viewportHeightPixels,
  visible: true,
});

planet.setQuality('high');
const stats = planet.getStats();
planet.dispose();
```

把实心地表、海水／熔岩、晶体与近景装饰、云层、大气分组管理。最终接入者应该能够单独禁用或替换它们，而不必重写全部星球代码。气态风暴可以单独封装，禁止伪装成固态地形来复用地面流程。

## 6. 性能与实现优先级

- 全部星球共用一个 renderer 和帧循环。允许只精细渲染当前选中的星球，其他星球暂停更新；没有必要同时维持四颗星球的最高精度。
- 用地平线／视锥裁剪、屏幕空间误差和有上限的块缓存控制地形开销；晶体、碎石等用实例化或等效批处理。
- 地形生成异步化并限制并发、每帧工作量和缓存容量。Worker 失败时保持已有可见网格，采用小预算补充，不能阻塞主线程同步生成整颗高精度星球。
- 气态高成本效果集中在相机附近或少量风暴区域；不要对整颗巨星无条件执行最高成本体积采样。
- 标准档以桌面浏览器 `1440 × 900` 下流畅交互为目标，优先达到稳定 30 FPS，硬件允许时争取 60 FPS。报告实际环境与测量结果，不要编造帧率或“零显存泄漏”的结论。
- 实施顺序建议为：先打通一颗固态星从全貌到地面的连续 LOD，再做三种固态地貌差异，随后完成气态近景，最后优化和补齐演示资料。
- 如果需要取舍，优先保留四类辨识度、真实近地几何、连续缩放和气态层次。不要用精美 UI 掩盖核心渲染未完成，也不要省略其中某类星球后宣称全部完成。

## 7. 验证与交付

请实际启动 Demo、用浏览器操作并检查渲染。交付时至少包含：

1. **完整可运行源码**：独立目录、依赖与锁文件、启动／构建命令、本地资产；不要只交一张效果图、一个压缩脚本或一份架构说明。
2. **README**：操作方法、模块结构、接口和坐标约定、四类生成规则、LOD 方法、预算／缓存上限、已知限制、第三方资源授权。
3. **四类对照截图**：每颗至少远景、轨道、低空、地面／云顶四张，记录种子、半径、画质和相机位置；同一颗的四张必须能追踪到同一个主要地标。
4. **连续缩放动态演示**：展示四颗从全貌接近到地面／云顶，再返回全貌的过程；额外展示气态风暴运动。必须来自实际运行，不用静态截图拼成“动画”。环境无法录屏时如实说明，并提供可直接复现的相机演示路径。
5. **验证记录**：报告实际测试的浏览器、硬件信息可用性、分辨率、画质、帧耗时与资源统计。检查极区、接缝、晨昏线、云层内外、快速缩放、连续切换和释放资源后的稳定性。

每颗固态星至少在两类明显不同的区域落到近地视角并横向移动，例如海岸与山脉、火山口与台地、峡谷与沙丘。不能只证明一个固定机位看起来很好。

下面这些情况均不算完成：

- 只有四个不同颜色的球，地貌骨架基本相同。
- 放大只提高贴图分辨率，没有局部真实地形几何。
- 靠近后切到另一个平面场景，远近地标对不上。
- LOD 切换让山峰移动、裂谷改变、地面闪洞或相机穿地。
- 气态星只是带旋转纹理的实心球，进入云层后没有可信深度。
- 单个截图漂亮，但不能连续操作，或者几次星球切换后性能持续恶化。

请在全新独立目录工作，不覆盖已有游戏实现，不读取或修改正式存档。无需账户或后端服务。若在原项目的本机环境预览，使用 `8390` 端口，不占用或请求 `8289`；如 `8390` 已被占用，先报告情况，不要擅自结束其他服务。

最终请给出可运行的交付物、启动方法和实际验证结果，并清楚指出哪些效果已经完成、哪些仍有限制。接入游戏的工作留给后续开发者。
